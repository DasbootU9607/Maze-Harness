# Planning beyond one release

Use this guidance when the requested room should require thought and several connected operations. A compact mechanism demonstration can have a different scope. These are design heuristics inferred from maps and engine behavior, not statements from the original author or a validated human difficulty scale.

## Extend the dependency, not the approach

A relative offset can disengage a contact chain and release another group despite a fixed boundary. That spatial insight may need only a few pushes. Lengthening the walk to those pushes does not deepen the dependency. Give the release a necessary prerequisite or consequence involving the same limited space.

## Design a chain of useful changes

Before drawing cells, write a short dependency sketch. For each intended edge, name the blocking cell or inaccessible stance, the preparation that changes it, and the later action it enables. Useful options include:

- **Prepare a stance:** another displacement exposes the correct face of the boundary-constrained group. The player must be able to reach it after preparing it.
- **Borrow a passage:** a useful intermediate position occupies the eventual route or goal; a later operation makes restoring access possible. Test whether movement in opposing directions is actually necessary.
- **Reuse clearance:** the bay needed for one group's offset is later needed by another group or by the player. Check both occupancy and access through each arrangement.

Choose an option because of the goal, not to add an arbitrary phase quota. For a substantial room, start with preparation, dependent operation, and completion as three functional stages, and make at least one stage constrain a later choice. If removing walking leaves only one independent release and a final approach, treat it as a demonstration and deepen it before claiming the requested planning depth.

Record each stage as `(all group poses, reachable player region)`. Reserve the next pushing face and the route to it; a geometrically free destination is not enough. Make useful protrusions, boundary stops, and parking spaces readable. Avoid unrelated obstacles that merely hide the relevant shapes.

## Review the claim

1. Replay a full solution with the actual objective. Compress walking and repeated same-direction group pushes into a short account of what changes. Input counts and compressed runs describe that witness, not minimum decisions.
2. Freeze each claimed necessary group, preserve relative offset, and exclude claimed key directional moves. Record any complete bypass and revise the explanation or geometry.
3. To claim A is needed before B, use a first-B opportunity search with A forbidden and a positive control. Full-goal freezing alone does not prove an order. Use the existing preparation checks where their endpoints match the design.
4. Link the fixed boundary to the dependency through the controlled wall comparisons in [usage](usage.md). Removing an unrelated wall cannot establish this mechanism.
5. For a claimed return, exclude each opposing direction separately. Exhaustion in both tests proves both occur somewhere; it does not prove return to an exact pose or one particular ordering.

Choose endpoints that represent the claimed progress. If the tool first retreats left, its next right push may merely undo that retreat. A first-right opportunity is then the wrong test for leaving the workspace. Use a specific progress state, such as the full tool entering the next region, with the goal as a bypass and a positive control. State the endpoint explicitly; do not interpret a harmless undo as a disproof of a different dependency.

Deliver a small table of intended dependency, observed state change, exclusion result, and any limitation. If a human trial is available, record whether the player noticed the independent groups, predicted the enabling move, and revised a plan after a failed approach. Time and mistakes are observations, not a universal score. Without that trial, describe the room as structurally tested and intended to be challenging.
