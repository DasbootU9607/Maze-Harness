# Deriving a new design

Start with the complete endpoint and work backward through the operations that make it reachable. A tool at the boundary is not the player at a usable doorway. Specify room-local access or an actual crossing explicitly; gem-free default completion is insufficient.

Read [mechanism logic](mechanism-logic.md) before layout and record its current SHA256. Select functions through the [cross-case comparison](reference-library.md), [catalog](reference-catalog.json) and [difficulty guide](difficulty.md). Begin with [design-template.json](design-template.json), whose geometry, events and routes remain empty.

## Derivation sequence

1. Identify the last useful shield operation and the player's route from it to the complete goal. Leave an actual free exit approach when a tool remains parked nearby.
2. Identify that operation's input member, direction and reachable player stance. Check current gate occupancy and the complete intended translation, not just an anchor path.
3. Determine how the tool and player acquire these positions. If the tool is initially available, connect the preceding operation to its input side. If it needs placement, plan both that preparation and the later approach; they may use different tools.
4. Choose individual or contact-chain delivery according to the useful arrival. A chain requires actual directional contact and clearance for every member. Its arrival must allow the intended separation and later inputs.
5. At each change of role, decide whether the next operation uses another shield, the same shield from a new side, or clear ground. Trace ordinary access to that stance before committing the earlier move. A traversed gate does not stay open.
6. Retain each tool only with a named later duty; parking can preserve that duty. Release it when the demonstrated remaining plan finishes without moving it again. Then choose geometry and replay the complete plan.

These decisions need not occur once each or follow a fixed source sequence. BxC's joint transport and preparation are optional branches; BxB shows that individual pushes can support a complete coordinated passage. Choose block count, direction order and shape autonomously. A compact request may isolate one relation. A composed design connects changes of useful access, not arbitrary walking detours or repeated pushes.

## Operation worksheet

For each role change, write the following before assigning coordinates. This is a reasoning worksheet, not an implemented extension to the JSON contract.

| Item | Required answer |
| --- | --- |
| Intended consequence | Which next operation or final route becomes available? |
| Input | Which actual member, direction and player stance make the current push executable? |
| Enabling preparation | What placement or preceding approach creates that input? If already available, say so. |
| Delivery | Which complete groups move, which contacts propagate movement, and is support/clearance legal? |
| Continuation | How does the player ordinarily reach the next input side? Does another tool stay usefully placed during that route? |
| Remaining duties | Which tools are active, parked for later use or released? Name the later action for every retained tool. |
| Evidence | Which full replay, contact assertion, branch comparison or scoped search supports the stated claim? |

## Diagnose a failed continuation

| Failure | Revise and check |
| --- | --- |
| The tool arrives but the player cannot use it | Derive the input side and its ordinary approach before fixing the destination. |
| The return crosses gates vacated by the tool | Recompute the actual gate state and provide a reachable connector or different operation order. |
| Joint delivery strands a tool | Revisit the shared destination and the actual separation inputs; arrival alone is insufficient. |
| Parking destroys later access | Preserve the future placement and the approach together, then replay the intervening operations. |
| A shield reaches the boundary but blocks the exit | Keep a genuine free door slot and verify the player's final approach. |

For a preparation claim, compare reachable ordinary branches with and without the proposed preparation. Match player/helper approach conditions where practical; observe the changed next action, then replay the positive continuation to the goal. A decorative event counter does not establish causation. Whole-goal bypasses and global necessity need separate compatible searches. Do not impose a doorway center-cell condition without a functional reason.

The included helper verifies unchanged official references only. It is not an authored-map builder or a transfer certificate. A requested new map needs its own build, ordinary full-goal replay and causal controls.
