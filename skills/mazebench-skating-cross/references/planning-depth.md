# Connected functional stages

Default authoring requires at least three stages connected by necessary access or pose dependencies. One cross may serve all stages. Do not import the non-ice skills' two-group or unit-translation contracts.

Name a real conflict: a turning stop is absent, the next pushing side is inaccessible, an arm collides too early, parking blocks a later ray, or clearing the gem removes the required brake. The stage outcome enables subsequent useful work.

Before layout specify the full objective, connected footprint/height, complete ice/wall footprints, functional poses, stopping states and input stances, swept clearance, collision members, restoration space and doorway route.

Freeze the group at each selected pose and search the directed ordinary-move graph. Compare stops, next stances, gem/doorway access and gained/lost positions. Equal stop counts can hide changed useful positions.

For a preparation claim, search before the first specified event, stopping at the real goal or a legal next-event opportunity and excluding event edges. Run a positive control, then forbid preparation with the same endpoint. Require exhaustion. For restoration after parking, keep explicit analyzer history in search keys and require it at the endpoint.

All-solution claims need all-history checks; selected-state freezes remain local. Replay and retain bypasses, then narrow the claim or repair geometry.

More inputs, longer slides, same-direction pushes, unrelated obstacles and milestones with no access effect are not functional stages. Count controls complement dependencies and are not human-difficulty measurements. The reference's final chain is an example, not a universal compass order.
